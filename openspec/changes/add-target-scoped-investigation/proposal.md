# Proposal

## Why

当前排障需要人工收集日志、查询集群和数据库，再指挥 Agent 逐步调查，定位过程慢且难以复用团队经验。我们需要一个以插件扩展的排障服务：给定日志和明确目标后，Agent 自主调查并在聊天中返回证据，同时支持多个集群及后续消息平台、执行引擎和数据源的接入。

## What Changes

- 新增 Redis 只读排障插件，封装 Redis 官方 MCP Server，按目标固定连接与 DB；白名单开放服务器状态、游标扫描和有界数据读取，凭证仅交工具后端，不提供写入或任意命令。
- 建立 TypeScript 插件宿主。Core 负责排障事件、会话、目标范围、配置解析和执行协调；执行引擎、诊断工具及消息渠道均通过插件接入。公共输入、证据和报告合同不依赖具体引擎、数据源或聊天平台。
- 插件可通过配置加载、启用和组合，并声明所需配置与能力。新增符合合同的插件无须修改 Core 或增加按厂商名称判断的分支；插件加载或配置失败应明确报告。首版实际接入均使用插件机制，不为未来平台创建空实现。
- 首个执行引擎插件接入 Codex，由 Agent 根据发现自主选择工具并继续查证。工具提供真实数据，Skills 提供系统背景、排障知识和证据要求，并可随插件或独立知识包提供。
- 首版交付 Lark 渠道插件：使用应用机器人接收群内发起的排障请求和追问，反馈受理状态、报告及失败提示。消息事件统一转为平台独立的排障输入，结果由渠道插件发送和呈现；后续钉钉、企业微信通过新增渠道插件接入。
- Lark带调查编号的回复末尾展示可复制的追问、状态、取消、继续及失败投递重试命令，并提示在原群@机器人；提示随完整逻辑回复分块及持久化，不重复附加到每个分块或重试消息，REST回复不增加Lark操作文案。
- Lark新回复使用卡片展示：正文突出非空调查内容，证据用短编号并保留完整对照，调查/轮次编号、用量和命令折叠展示。渠道通过公共纯渲染合同产生可持久化的文本及私有载荷，Core不解析厂商格式；旧文本投递计划保持可重试，REST保持原有展示。
- 内置REST渠道供curl或程序调试，使用配置固定调用身份和Bearer Token，将提交、追问与控制请求转为同一消息合同；支持分页轮询持久化回复，复用既有授权、去重与调查协调，不要求Lark可用。
- 渠道配置声明连接凭证，可选声明企业、群、用户和排障目标过滤；省略时使用渠道可收到的来源及已登记目标。调查通过事件编号关联，当前调用者的目标授权控制读取和操作；每轮回复绑定自己的触发平台与会话，平台消息编号不跨来源猜测，避免误关联；重复消息投递不得重复启动调查。排障核心可独立验证，Lark 群内交互是首版端到端验收入口。
- 引入按环境组织的排障目标配置：一份全局配置负责默认 Agent、聊天入口和授权，每个目标文件集中声明自己的工具、连接及知识。不同目标可选不同工具、同一插件可有多个独立实例，共享数据库或仓库通过显式引用表达。内置插件使用短名称和默认部署路径，日常配置无需填写模块入口和内部实例 ID。
- 各类连接设置、Agent 运行参数及其所需凭证从配置文件加载，支持直接保存连接地址、用户名、密码等值，也支持引用独立的 kubeconfig、证书文件；不要求首版接入外部密钥管理服务。真实配置保存在运行环境中并排除出版本控制，仓库仅保留不含真实凭证的示例配置；配置文件的拆分方式在设计阶段明确。
- Codex认证支持apiKey、apiKeyFile或authFile三选一，authFile可引用已有Codex登录缓存，支持目标文件相对路径与~/路径。仅导入认证数据，服务专用凭证目录保留Codex原生刷新，调查HOME/技能/工作目录仍独立；不导入个人config、MCP或技能。默认仅记录模型确认用量及完整性；仅全局runtime.maxModelTokens显式配置时启用上限，API模式预计数，ChatGPT模式按原生thread累计用量的差额检查，明确不保证生成前Token硬限额。内置提示集中在独立Markdown文件，动态上下文单次填充。
- 配置按排障目标分别绑定和使用。集群、数据库及 GitHub 凭证由对应工具插件读取，Agent 运行凭证由执行引擎插件使用，Lark 等消息平台凭证由渠道插件使用；凭证不进入 Agent 提示、工具返回、调查记录或报告。启用插件不自动授予其他目标或渠道的凭证与权限。
- 每次调查绑定一个明确目标，使用独立会话和证据记录；追问沿用原目标。Thread 只接收当前目标筛选后的上下文和工具清单，全量配置留在宿主，不将其他集群的配置或凭证注入该 thread。工具按绑定范围执行校验，并发调查不共享可变的集群上下文或数据库连接选择；创建和恢复会话时均校验目标一致性。
- 首版隔离验收聚焦防止串目标：调查 A 时，不装配 B 的连接、不允许工具改绑 B，也不混用 B 的证据；显式共享的数据源按授权范围使用。Codex模型的本地文件访问另由原生权限档落实，不为每个thread新建容器。
- 默认使用Codex原生权限档限制模型本地命令：当前工作/临时目录可写，已装配技能只读，其余文件默认不可读；额外目录由agent.config.filesystem显式声明。原生网络代理阻止未授权Unix socket，公网访问保持可用；不自研沙箱或回退为全权限。
- SSH连接作为目标tools中的独立插件，一个实例固定一台服务器，同一目标可组合多台服务器；使用ssh2处理密码、私钥、私钥解锁口令及服务器要求的公钥后账户密码。凭证仅由宿主持有，调用不允许改host/用户/认证；通过已信任known_hosts固定主机身份。
- SSH工具只提供通用远程command调用，模型自主选择诊断命令，不逐条封装kubectl或日志。任意命令能力标记readOnly=false，不把提示词或元数据当作远端只读控制；生产变更仍不属于排障任务，远端账号权限单独管理。输出经宿主证据/脱敏/预算与取消边界，远端终止未知时明确报告。
- Codex默认保留普通本地命令、目录权限及skills，移除引擎SSH连接字段、专用agent及socket例外；SSH插件通过同一注册工具合同供所有引擎使用。
- 目标可用 skills 路径列表声明本地技能目录，启动时发现并校验技能包；创建及恢复调查时将当前目标技能装配到独立运行时目录，由 Codex 原生发现和按需读取。保留脚本、references、assets 及执行标志，技能内容指纹参与恢复范围；不自动下载技能或安装其依赖。
- 第一批工具插件复用现成 MCP：K8s 使用 `containers/kubernetes-mcp-server` 读取 Pod 日志（含可用的上一次容器日志）、资源状态与事件；数据库使用 DBHub 查询结构、授权业务数据和运行状态，首个实际接入与验收环境为 PostgreSQL，其他数据库按组件能力和验证结果支持。插件负责配置、目标绑定、权限约束、生命周期和证据转换，不重新实现每个数据源的查询工具。
- K8s MCP 每轮只装载当前目标的单集群kubeconfig，透传上游core工具及真实副作用标签；namespace、资源及动作权限交给Kubernetes RBAC，不在宿主重复维护白名单。保留目标连接隔离、凭证脱敏、生命周期和结果预算；排障目标不自动授权生产变更。
- 源码访问采用 GitHub 官方 MCP，由 Agent 按需搜索和读取目标允许的仓库文件、提交及 PR 差异，并查询相关发布信息。配置文件只提供目标GitHub凭证，权限交给Token，直接转发官方MCP只读目录及原生tag/branch/SHA/搜索参数；记录实际请求版本，线上版本对应关系无法确认时在报告中说明，不阻止读取。
- 报告区分已确认事实、疑似原因和缺失证据，保留证据来源、查询时间与目标信息；查询失败、日志已丢失、访问被拒或调查超时必须明确呈现，不能解释为没有异常。
- 新增集群优先通过配置完成，新增引擎、数据源和消息平台通过插件接入，排障经验通过 Skills 和参考资料积累；首版落实 Codex、K8s、数据库及 GitHub MCP 工具和 Lark 渠道的插件接入。

Lark接入简化：仅应用凭证必填，机器人身份启动时自动获取，租户身份由认证事件携带；渠道routes及企业/群/用户/目标过滤均选填，省略使用渠道可收到来源和已登记目标，显式过滤及空列表拒绝仍有效。保留单调查固定目标、每轮来源溯源和目标授权；来源不作为调查归属，详见 `decouple-investigations-from-channels`。

## Capabilities

Lark交互文案统一：环境选择及拒绝也通过渠道渲染合同展示中文卡片，环境清单只来自当前来源授权；状态/取消/投递重试仅发送一条操作结果，内部状态和诊断代码进入详情，保留机器响应及调查关联语义。

Lark新回复原生引用各自触发的用户消息，受理/报告引用该轮请求，追问结果引用追问本身，群内并发请求可直接分辨；引用与投递计划持久化，旧计划和重试的原有行为保持。

显式引用同群他人消息并@机器人时按需读取一条原文作为排障输入，支持文本/富文本代码，已知调查仍直接续接；保留一次受理的上下文快照、授权/输入预算和读取失败提示，无关群回复不触发。实际读取取决于应用的消息及群权限，不自动开通或扫描聊天历史。

GitHub仓库列表改为选填：省略时由目标Token权限决定可读仓库，Codex可自行搜索定位；填写时保留本地仓库限制和运行版本映射。prod使用独立凭证文件接入，不影响dev工具集合。

### New Capabilities

- `redis-diagnostics`: 通过官方 Redis MCP 在目标固定连接读取状态、键类型/TTL及必要数据，控制扫描/结果预算并明确分页、认证失败与 ACL 权限边界。
- `plugin-system`: 管理插件的配置加载、启用、能力注册及生命周期，使用公共合同组合执行引擎、诊断工具、消息渠道和相关知识，支持扩展接入而不修改 Core。
- `diagnostic-targets`: 从配置文件加载排障目标、连接设置和凭证，管理集群、数据库及 GitHub 仓库引用并校验访问范围，隔离各目标的连接配置与各次调查的上下文。
- `agent-investigation`: 从日志和目标发起自主调查，加载相关知识、工具与源码上下文，支持会话追问，并输出可核查的调查记录和报告。
- `chat-investigation`: 通过渠道插件将请求、追问和排障事件关联，校验来源及目标范围，处理消息去重与结果回传；内置Lark及用于curl调试的REST渠道，支持后续扩展其他消息平台。
- `kubernetes-diagnostics`: 在目标允许的集群及 namespace 内读取 Pod 日志、资源状态和事件，处理多副本、多容器、日志保留限制及查询失败。
- `database-diagnostics`: 通过可复用的数据库工具插件查询目标范围内的结构、业务数据和运行状态；首版验证 PostgreSQL，限制访问权限、查询耗时及结果规模，并保留数据库方言和诊断能力差异。
- `source-code-access`: 通过 GitHub MCP 读取目标允许的仓库源码、提交及 PR 差异和发布信息，将源码证据关联到明确版本，并呈现版本未知或访问失败的限制。

### Modified Capabilities

无。本 change 的起点是仅包含开发、类型检查和构建命令的空 TypeScript 骨架，没有需要修改的现有规格或业务行为。

## Out of Scope

- 钉钉、企业微信等后续渠道的实际实现，以及自动告警源接入；首版完成 Lark 内发起请求、追问和接收结果的流程。
- 重启、回滚、扩缩容、配置修改、数据库写入等生产变更。
- SLS 查询接入、历史日志平台建设、其他数据库的全面验收及第二种 Agent 引擎实现。
- 本地 Git 仓库克隆、源码同步和缓存服务的专门建设；首版托管源码工具使用 GitHub MCP，原生命令按当前目标知识自主调查，不增加另一套源码同步服务。
- 对恶意宿主/插件或操作系统漏洞的强隔离保证；首版使用Codex原生权限落实本地目录和socket边界，不建设自有沙箱平台。
- 将完整排障流程固定成宿主编排步骤；插件市场、运行中热插拔、对不受信任插件代码的沙箱执行，以及分布式任务平台和多用户管理后台均不在首版范围。
- 缓存、消息队列、外部 API、历史指标和调用链等数据源的全面接入；保留按真实故障需要扩展的方式。

## Impact

- 这是项目首个行为 change，将新增插件宿主、目标配置、执行引擎与工具插件、Lark 渠道插件及调查产物；不存在旧业务接口或数据的兼容迁移。
- 预计封装 Codex 官方 TypeScript SDK，K8s 接入采用 [Kubernetes MCP Server](https://github.com/containers/kubernetes-mcp-server)，数据库采用 [DBHub](https://github.com/bytebase/dbhub)，源码接入采用 [GitHub 官方 MCP Server](https://github.com/github/github-mcp-server)，Lark 接入优先复用 [官方 Node SDK](https://github.com/larksuite/node-sdk)。各插件的部署方式、版本、许可证、维护与安全记录在 design 中记录并在实施时复核。
- 接入环境需要配置集群、数据库及 GitHub 仓库的读取连接与凭证、运行版本映射，以及 Lark 应用连接信息和群/用户到目标范围的映射。已按用户提供的 dev SSH 入口验证只读登录；真实集群/数据库取证、版本映射与 Lark 试点仍待确认。
- 验收重点是：Lark 群内可发起和继续一次带证据的调查，重复消息不重复执行，结果回到正确会话；多目标并发调查不串用连接、凭证或证据；GitHub 源码版本可核查，工具失败和证据不足得到明确说明。
- 插件扩展验收使用最小测试插件接入现有合同，证明新增引擎、工具或渠道无需修改 Core；第一批真实接入也须走同一插件路径。配置或插件加载失败不得静默切换到其他目标、渠道或引擎。
- proposal、design、七份能力 specs 与实施 tasks 共同描述首版计划，供评审及后续实施；规划完备不表示业务已实现或真实环境已通过验收。
